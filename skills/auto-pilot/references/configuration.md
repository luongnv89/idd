# Configuration defaults — full rationale

`/auto-pilot` reads `.idd.yml` once at start (never re-read per iteration).
The canonical schema lives in `references/docs/config-schema.md`; this file expands the
per-key rationale behind each `autopilot.*` default. The SKILL.md body carries
the bare default values — read this when you need the *why* or the edge-case
behavior.

- `autopilot.mode: balanced` — merge mode. See **Merge Modes** in SKILL.md for the three values.
- `autopilot.merge_partial: false` — never merge a PR with unresolved fixable review issues unless explicitly opted in. Only honored when `mode: aggressive`.
- `autopilot.max_iterations: 10` — maximum issues to process before stopping.
- `autopilot.max_parallel: 1` — maximum resolver lanes in one bounded fan-out (`1..8`), drawn from one persisted `summary.parallel_groups` entry; everything after resolver fan-in stays serialized. A lane whose worktree setup fails **never falls back in-place**. `1` is the sequential in-place path. Lanes and ownership: `references/orchestration.md`.
- `autopilot.review_cycles: 3` — maximum fix attempts per PR. After this many cycles, if issues remain the behavior depends on `autopilot.mode` (see *Merge Modes*). The script pre-pass in issue-pr-review handles lint/format, so 3 LLM cycles suffice for logic issues. A cycle = one fix attempt + one review pass. Confirmation-only review passes (spawned after a PASS to verify, without a preceding fix) do not consume a cycle.
- `autopilot.auto_merge: true` — **legacy** field, retained for backwards compatibility; it is ignored whenever `autopilot.mode` is set. How it resolves otherwise is stated once in the *Resolution rules* under *Merge Modes* in SKILL.md.
- `autopilot.pause_on_failure: false` — skip failed issues and continue to the next one (autonomous default). When false, the auto-pilot logs the failure, adds the issue to the skip list, and moves on. Set to true only if you want the loop to halt on every failure for manual inspection.
- `autopilot.skip_labels: ["wontfix", "blocked", "do-not-merge"]` — skip issues with these labels.
- `autopilot.critical_labels: ["critical", "priority:critical"]` — labels that mark an issue as critical. When a critical issue has unresolved review problems after all cycles, the loop stops and asks the user for a decision instead of auto-creating a follow-up.
- `autopilot.respect_dependencies: true` — honor `Depends on #N` / `Blocked by #N` markers in issue bodies. Before merging PR-A, verify that every dependency referenced from issue A is closed and its PR merged; if not, do not merge — print a structured alert, record `blocked_by_dependency`, leave PR-A open, and continue to the next eligible issue (the run is not paused). Set to `false` to skip the gate entirely. See *Phase 5 — Merge* in `references/phases/phase-5-merge.md` for the full check.
- `autopilot.triage_cache_max_age_minutes: 60` — how old `.idd/triage.json` may be and still be reused by *Step 1.1a*'s cache gate. Age is only half the test: the gate also requires that no commit landed after the cache's own `updated` timestamp, so a cache written a minute ago is still `stale` once a merge lands. Set `0` to refuse any pre-existing cache, so the run always starts with a full triage — matching `references/docs/config-schema.md`'s "`0` disables reuse". It is **not** a per-iteration off-switch: *Step 1.1a* is evaluated once, before the first iteration, so `0` forces the full triage on iteration 1 and nothing after it. `retriage_every: 1` is the key that forces a full triage every iteration. The gate fail-safes to `stale` on any doubt, so a wrong value costs a re-triage and never a wrong pick.
- `autopilot.retriage_every: 0` — force a full re-triage every N-th iteration, counted from the 1-based `{i}` at the top of the loop (`i % N == 0`); `0` (default) never forces one. The check is **not** gated on a merge, so `N: 1` forces a full triage every iteration — including under `mode: conservative` and on iterations that leave a PR open. *Step 1.6*'s incremental update is removal-only, so it stays correct as long as the backlog only shrinks; set this on long unattended runs against a repo other people file into, where new issues would otherwise not be seen until a pick miss. A pick miss forces a re-triage regardless of this value, and *Step 1.1b*'s live open-issue read is what makes that miss reachable on a reuse iteration — a newly filed issue is in that set and not in the cached order, which is the drift the retry recovers from.
- `autopilot.quarantine_after: 3` — how many **consecutive** `failed` runs an issue may have before *Phase 2.3* quarantines it. `0` disables the check outright: the script is never invoked and no label is ever applied. Three is chosen to be past the noise: one failure is often a flaky test or a transient API error, two can still be the same transient cause, and by the third the issue is reliably costing a full resolve-plus-review every run for nothing. The count is *consecutive* and derived by scanning `.idd/runs.jsonl` backwards to the issue's first non-`failed` record, so a single success anywhere in between resets it — an issue that was fixed and later regresses starts its streak over rather than inheriting an old one.
- `autopilot.quarantine_label: "auto-pilot-quarantined"` — the label *Phase 2.3* applies at the threshold. **SKILL.md's *Configuration* step appends it to the effective `skip_labels` set** as part of the same one-time load, which is the whole read side of the feature: the pick predicate already skips `skip_labels`, so there is no second gate to evaluate and no way for the two to disagree. The shipped default `skip_labels` does not contain the label, so this append is load-bearing, not tidy-up.

  **Why the label is the source of truth, and not a state file.** "Skipped until the label is removed" needs a durable, human-visible record: a label survives a clone, a new machine and `rm -rf .idd/`, and a human can see and clear it. A state file would be a second source of truth that can *disagree* with the label, and `run-state.json` is single-run with a closed key set.

  **Why the counter fails open.** `runs.jsonl` is gitignored, best-effort, and deletable, so it can only ever be *progress toward* a quarantine, never the quarantine itself. When it is missing or unreadable the script still prints its line with `streak: 0` and exits 4, and the loop skips the check rather than guessing. The asymmetry is deliberate: a missed quarantine costs tokens on one more attempt, while a wrong quarantine silently parks a real issue that nobody is watching for. Losing the log therefore loses progress toward a quarantine and never an existing one — the label is untouched.
- `autopilot.max_open_prs: 0` — cap on open IDD-convention PRs waiting for review (`0..50`); `0` (the default) is no cap and no API call. Checked at the top of each iteration, and a fan-out takes only the slots left under it.
- `autopilot.max_runtime_minutes: 0` — wall-clock budget for the whole run, measured from the `started_at` in `.idd/run-state.json`; `0` (the default) is unbounded, for anyone who does not want a clock. Set it for a run under a CI job timeout, a nightly window, or a metered API budget. It is a **start gate, not a kill switch**: it is evaluated at the top of each iteration and around any rate-limit pause, because the orchestrator cannot interrupt a spawned subagent, so an iteration that begins inside the budget always finishes and no PR is abandoned mid-review. It also bounds a rate-limit pause — a `reset` that falls past the budget stops the run cleanly instead of sleeping through it. Expect an overshoot of at most one iteration; size the value accordingly.
- `resolver.claim_label: "agent:working"` — the label `/issue-resolver` holds while it works on an issue (`""` turns the claim off). *Configuration* appends it to the effective `skip_labels` like the quarantine label, so the loop never picks an issue another run is resolving; *Step 1.2b* records it `blocked_label`. A claim never expires, so an issue a killed run left claimed waits for a person to remove the label — except an issue in *Step 1.0*'s resume set, whose resolver this run spawns with the same `run_id` and so reads the claim as its own; that issue alone is exempt from the claim-label skip.
- `triage.route.label_prefix: "route:"` — *Configuration* appends `{prefix}needs-human`, `{prefix}needs-info` and `{prefix}duplicate` to the effective `skip_labels`, the same one-time append as the quarantine label, so an issue `/issue-triage --route` held back is never picked or resolved; *Step 1.2b* records it `blocked_label`. Consumers read only these restrictive labels: `{prefix}agent-ready` is not an allow-list and grants nothing, so an issue with no route label goes through the ordinary pick rules. The gate is label-only: with `triage.route.label: false` (the default) nothing is held back.
- All `resolve.*` and `triage.*` settings are inherited by the sub-skills.
