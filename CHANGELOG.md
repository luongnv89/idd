## [Unreleased]

### Features
- **security:** ship an installable local pre-commit secret gate (#340) — `.githooks/pre-commit` delegates staged index blobs to `gi-secscan.py --staged` and preserves its output and exit status; `bash scripts/install-hooks.sh` enables it per checkout without overwriting another hooks path. CONTRIBUTING documents install, verification, removal, and the `--no-verify` limitation, while a hermetic integration test proves benign commits pass and a staged canary is blocked.
- **ci:** measure Python coverage over the shared script entry points and pin the floor in CI (#333) — ~3.5 kLOC of stdlib helpers in `src/shared/scripts/` had zero coverage measurement (F-TEST-001, plan task 0.1). `.coveragerc` scopes the measurement to that tree and pins `fail_under = 40` — the first measured value; raising it is deliberate Sprint 6 work, and a regression now fails CI. `scripts/coverage-run.sh` exercises every entry point hermetically and offline (`--help` everywhere plus behavioral invocations with payloads copied from `tests/`: config merge, dependency parsing, dup-score stdin request, run-log echo and failure-streak, stack detection over this repo, run-state init/read/report, the documented triage-graph payload, model-cache lifecycle, rate-limit arithmetic, branch derivation), then enforces the floor through `coverage report` itself and publishes text, XML, and HTML reports. A dedicated `coverage` job in `dist-check.yml` installs coverage.py on Python 3.11, runs the runner, and uploads `coverage-report/` as a run artifact. `tests/test-coverage-floor-333.sh` pins the wiring structurally: scoping, integer pin, committed-0755 runner covering every entry point, enforcement via `coverage report`, artifact upload, and no diverging command-line override.

### Fixes
- **scripts:** bound config discovery at the working-tree root (#339) — `gi-branch`, `gi-triage-graph`, and `gi-model-cache` now use the same validated `git rev-parse --show-cdup` ceiling as `gi-config` and `gi-secscan`, so a `.gitissue.yml` above a checkout cannot alter branch, triage, or model-cache behavior. A behavioral fixture covers hostile ancestors, nested repo-root discovery, and config/secscan ceiling parity.

- **auto-pilot:** harden the unattended loop — quarantine, rate-limit pause, runtime budget, retry contract (#259) — a run with nobody watching had four ways to waste itself. A permanently broken issue was re-picked **every** run, because the skip list it landed in is a single-run, in-memory list; a rate budget below 200 was a hard stop with the remedy "wait for the budget to reset, then re-run", addressed to a reader who is not there; there was no wall-clock bound of any kind, only `max_iterations`; and *Retrying after transient failures* was listed as an auto-decide category with **no retry contract anywhere in the skill** — `grep backoff` over the whole thing returned nothing. All four now have one. **Quarantine:** after `autopilot.quarantine_after` consecutive `failed` runs (default 3, `0` disables) the issue is labelled `autopilot.quarantine_label` and skipped until a human removes it. The **label is the durable state** — it survives a clone, a new machine, and a deleted `.gitissue/` — while the streak is a soft count derived from `runs.jsonl` by `gi-runlog.py --failure-streak`, its one read mode; that count deliberately **fails open**, so a missing or unreadable log reports `streak: 0` and nothing is ever quarantined on evidence nobody read. The read side is free: the label joins the effective `skip_labels` set at config load, so the existing pick predicate does the skipping and there is no second gate to disagree with the first. Quarantine is record-and-continue — it never stops a run. **Rate limits:** driver rule 4 now selects `.rate.reset` alongside `.rate.remaining` from the one call it already made, and below the threshold the run **pauses until reset and resumes** rather than stopping, provided that instant fits the runtime budget. The pause is chunked at 300s with a run-lock heartbeat refresh between chunks, which is what stops the 3600s lock TTL retiring a live run mid-pause; `gi-state.py` stays the single writer of `run.lock`. **Runtime budget:** `autopilot.max_runtime_minutes` (default `0`, unbounded) bounds the run from the run state's `started_at`, checked at the top of each iteration and around every pause — the only points where the orchestrator holds control, since it cannot interrupt a spawned subagent — so it gates *when new work starts*, never abandoning an in-flight PR, and stops cleanly with the report persisted and the lock released. **Retries:** new driver rule 5 is the single home of the classification (5xx, connection reset/timeout and a *secondary* rate-limit 403 with `Retry-After` are recoverable; 401, 404 and *primary* exhaustion are not, the last taking the pause path instead), with the 2s/4s/8s/16s four-attempt loop documented once beside its call sites and computed by a second new script, `shared/scripts/gi-ratelimit.py`. `/issue-creator`'s two contradicting "3 retries with 5s, 10s, 20s" statements now point at rule 5 instead of restating a different schedule, and every `.rate.remaining`-only call site across triage, creator and resolver follows the driver's new form.
- **auto-pilot, resolver:** persist resumable run state, take a run lock, and stop closing issues behind unmerged PRs (#257) — an interrupted `/auto-pilot` run had no memory: re-invoking it re-triaged from scratch, re-picked the issue it had been half-way through, and the resolver then met its own PR and reported the issue done, so an issue could be **closed behind a PR nobody had reviewed or merged**. Two concurrent runs in one working tree stashed and rebased over each other, and a run nobody watched left no artifact at all. - **auto-pilot:** triage once per run and update the cache incrementally (#258) — every loop iteration ran a full triage and bulk-fetched up to 100 issues *with their bodies* into the orchestrator's context, so the "lightweight orchestrator" promise cost roughly 50KB per iteration and degraded on long backlogs. Four changes, all shaped after the reuse gates #254 and #255 established. A new **Step 1.1a — Triage cache gate** runs *once*, above the loop, and sets `triage_cache = fresh | stale | absent`: `fresh` reuses `.gitissue/triage.json` when it parses, carries a non-empty `summary.suggested_order`, is younger than `autopilot.triage_cache_max_age_minutes` (default 60) and no commit landed after its `updated` stamp — the same commits-since signal `/issue-triage`'s cached view already computes, read rather than reinvented. Any doubt is `stale`, and `stale`/`absent` both run today's full triage byte-for-byte, so the gate can only remove duplicated work and never change an outcome. Phase 1's bulk list drops `body` (the field list still *ends* in `state,updatedAt`, which #256's *Step 0i* reads structurally), and **Step 1.2b** now fetches the one body an iteration needs after the pick, via `gi-issue.py` with the identical seven-field set — without that half, dropping `body` would silently degrade every resolver spawn from `supplied` to `partial` and restore the per-issue fetch #256 deleted. A new **Step 1.6** then updates the cached payload after each merge by **pure set removal**: drop the resolved number from `issues[]`, `summary.suggested_order`, `summary.parallel_groups` (dropping a group that empties) and every remaining `blocked_by`/`blocks`, flip an issue whose `blocked_by` just emptied from `blocked` to `ready`, recount rather than subtract, and append exactly one `history[]` entry. It is removal-only by necessity, not by taste: the ordering engine tie-breaks on `createdAt` and the persisted record carries only `updated_at`, so a cached payload cannot reproduce its own order — but deleting one node from a valid topological order leaves a valid one. Because Phase 1's bulk list was also the orchestrator's only *live* view of the backlog, a fourth step keeps that view without restoring the cost: **Step 1.1b — Live eligibility read** issues `gh issue list --state open --json number,assignees --limit 100` on a reuse iteration — two scalar fields, no bodies, a few kilobytes against the ~150KB a hundred bodies would cost — and is reused from Step 1.1's own list on a triage iteration. It supplies the three things a cached payload provably cannot: *Step 1.2*'s **Open** and **Not assigned** criteria (`.gitissue/triage.json` carries neither a GitHub `state` nor an `assignees` field, so without it an issue closed as `not planned` — which lands no commit for the gate's commits-since check to notice — would be picked and handed to a resolver), the live set the pick-miss predicate is defined over, and the empty-backlog stop that prints `✓ All issues resolved` on a reuse iteration. Any doubt is `unavailable`, never an empty set, and on `unavailable` the two criteria fall through to a post-pick re-check against *Step 1.2b*'s live record, which re-picks rather than spawning. A full re-triage still runs on a pick miss (once per iteration, never twice) or every `autopilot.retriage_every` iterations (default `0` = never), and any parse or write-back failure degrades to `⚠ Could not update the triage cache — re-triaging next iteration`. The new suite verifies the two load-bearing claims against the Python rather than the prose: the ordering engine's output is byte-identical with and without bodies, and a documented removal leaves an order that is a subsequence of the full-triage order with no dangling `blocked_by`.

- **resolver, review:** add a QA handoff marker so `/issue-pr-review` trusts a clean resolver PR (#255) — `/issue-resolver` finished a QA loop (review clean, tests green) and opened a PR; `/issue-pr-review` then re-ran the identical review machinery over the same unchanged diff, because nothing told it the PR had already been QA'd. The resolver now writes one machine-readable line as the **last line** of the PR body — `<!-- gitissue:qa v1 head=<sha40> profile=<light|full> cycles=<n> review=clean tests=<count>@<sha40> ui=<none|code|code+browser>:<clean|noted>@<sha40> -->` — and `/issue-pr-review` gains a **QA handoff gate**, the twin of the resolver's *Step 0h*: one state variable `qa_handoff = trusted | stale | absent`, `trusted` **iff** the marker parses **and** its `head=` equals the PR's `headRefOid` (now requested in Step 1's `gh pr view --json` field list, and added to the canonical `docs/platform-github.md` catalog). `trusted` collapses the cycle-1 cold-start reviewer **into** the existing fresh confirmation pass — a merge, not a deletion, so the one independent full-strength review a clean PR receives is the unbiased confirmation pass rather than a cold-start one; no reviewer spawn is saved, because the confirmation pass is itself fix-conditional and an unmarked clean PR already gets exactly one cold-start pass — caps the loop at `min(1, configured_cap)`, and skips the duplicated local test runs at Steps 2 and 4, but only when `tests=` is present and its SHA equals `head` (that SHA is carried separately because the resolver's final suite runs *before* its documentation step, which may commit; the field is omitted entirely when the resolver ran no suite). The code UI review is skipped only when `ui=` says that leg actually ran **and** its own `@<sha40>` equals `head` — `ui=none` skips nothing, and an unsuffixed `ui=` stays parsable but is never skippable — because that review runs before the resolver's QA cycles, so every QA fix commit lands after the diff it saw; the leg is split from the browser one because the code leg is environment-independent while the browser leg is fail-soft and skips on a headless host. Both SHAs are captured at the step that produces them, and a missing capture omits the field rather than defaulting to `head`. `stale` and `absent` take the byte-identical pipeline that already exists, and **any doubt is `stale`**: an unparsable or duplicated marker, a `head=` that is not 40 lowercase hex characters, a missing `headRefOid`. An unknown *extra* field is deliberately **not** doubt — it is ignored, never fatal, so a newer resolver can add a field without invalidating every marker for older reviewers. A human-authored PR carries no marker, so it is `absent` and completely unaffected. The trust model is stated in the prose rather than left implied: a PR body is **attacker-controlled** (`gh pr edit --body`) and `head=` binds without authenticating — an author can paste their own head SHA — so the design makes forgery **worthless, not impossible** by allowing the verdict to gate **only duplicated work**. `gi-secscan`, the lint/format auto-fix, Step 5's CI wait, the per-criterion acceptance-criteria verification, and the four traceability checks are an explicit **Never gated** list and carry no marker conditional at all; the reporter's suggested "AC verification in diff-confirm mode" is refused outright, because the resolver authors the Acceptance Criteria Verification table inside the very body being trusted. There is deliberately **no secret-scan field in any spelling** — its only possible consumer would be a safety gate, and open issue #274 is the standing proof this repo can lose one to repo-controlled input. The binding self-invalidates for the price of one recomputation: any commit this skill pushes — Step 2's lint/format auto-fix as much as a fixer's fix — moves the head and the marker stops matching, and the verdict is recomputed after **every** such push (the loop re-enters at Step 3, so nothing else would re-read the head); a body edit does not move the head, so the marker correctly survives one. `review.adaptive_depth: false` disables the gate exactly as it already disables the depth gate — **no new config key was added**, so the `config-schema.md` ↔ `gitissue-template.yml` parity pair is untouched. @luongnv89

- **skills:** ship `gi-secscan`, `gi-ci-wait`, `gi-issue`, and `gi-branch` (#252) — the second wave of deterministic scripts, replacing the four highest-frequency prose-executed procedures. `gi-secscan.py` is the pre-commit security gate as code: the same five rules as the canonical document (block on secret-bearing filenames and real API-key values, warn on large files, build artifacts, and protected branches), applied to `--staged` / `--working-tree` / `--range` / a stdin path list, printing one JSON verdict and **exiting 1 on a block**. That code is a verdict, not a runtime failure, and every call site says so explicitly — the default reading of a non-zero exit is "degrade", and degrading past a real secret is the one outcome the gate exists to prevent. Patterns extend per repository through a new `security.*` config section (`extra_secret_file_pattern`, `extra_secret_value_pattern`, `allow_pattern`, `max_file_size_mb`), which the script reads from `.gitissue.yml` itself.
