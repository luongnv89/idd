## 1. Outcome

After this refactor:

- A single source tree under `src/` holds all authored skill content, shared agent prompts, and skill-consumed runtime docs.
- A single build command (`./scripts/build.sh`) produces two distribution outputs:
  - `dist/skills/<name>/` — **committed**. Flattened, self-contained skills for any SKILL.md-compatible harness.
  - `dist/plugin/` — **built in CI, shipped as release artifact, not committed**. Claude Code plugin layout with `.claude-plugin/plugin.json` and plugin-root resources.
- The build is byte-deterministic: identical `src/` plus identical `build.py` produces identical `dist/` on any machine, any time. CI relies on this for the drift check.
- Cross-skill calls render correctly per output, with rendering chosen from the §6.0 experiment outcomes:
  - Standalone skills use `/issue-resolver` (slash auto-resolve) or `../<name>/SKILL.md` (sibling fallback).
  - Plugin skills use `/<plugin-slug>:issue-resolver`, `${CLAUDE_PLUGIN_ROOT}/skills/<name>/SKILL.md`, or `../../<name>/SKILL.md` (plugin sibling fallback) per ADR.
- CI fails if committed `dist/skills/` is out of sync with `src/`.
- CI validates flattened-skill self-containment and builds + validates the plugin tree on every PR; release jobs publish the plugin tarball.

- `assets/` stays at repo root. The build never touches it.
- The build is byte-deterministic (§4.1).

## 3. Authored Reference Conventions

Source files under `src/skills/` may use these logical references:

| Source reference | Meaning | Standalone output | Plugin output |
|---|---|---|---|
| `shared/agents/X.md` | shared agent prompt | `references/agents/X.md` | `${CLAUDE_PLUGIN_ROOT}/shared/agents/X.md` (B-1) or `../../../shared/agents/X.md` (B-fail + C-1) |
| `docs/Y.md` | skill-consumed runtime doc | `references/docs/Y.md` | `${CLAUDE_PLUGIN_ROOT}/docs/Y.md` (B-1) or `../../../docs/Y.md` (B-fail + C-1) |
| `templates/Z.md` | local skill template | unchanged path; content rewritten | unchanged path; content rewritten |
| `{{skill:issue-resolver}}` | cross-skill invocation token | `/issue-resolver` (A-1) or `../<name>/SKILL.md` (A-fail) | `/<plugin-slug>:<name>` (A-1) or `${CLAUDE_PLUGIN_ROOT}/skills/<name>/SKILL.md` (B-1) or `../../<name>/SKILL.md` (C-1) |

Final per-output path forms are selected by the §6.0 ADR. The build aborts if the ADR has not been committed by PR 3 build time.

**Worked example.** Source `src/skills/auto-pilot/references/subagent-prompts.md`:

```text
Use the {{skill:issue-resolver}} skill to resolve issue #{N}.
Naming: see docs/naming-conventions.md.
Subagent prompt: shared/agents/codebase-researcher.md.
```

**Auto-resolution rendering** (A-1 + B-1):

`dist/skills/auto-pilot/references/subagent-prompts.md`:
```text
Use the /issue-resolver skill to resolve issue #{N}.
Naming: see references/docs/naming-conventions.md.
Subagent prompt: references/agents/codebase-researcher.md.
```

`dist/plugin/skills/auto-pilot/references/subagent-prompts.md`:
```text
Use the /idd:issue-resolver skill to resolve issue #{N}.
Naming: see ${CLAUDE_PLUGIN_ROOT}/docs/naming-conventions.md.
Subagent prompt: ${CLAUDE_PLUGIN_ROOT}/shared/agents/codebase-researcher.md.
```

**Sibling-relative rendering** (A-fail, plus C-1 for plugin):

`dist/skills/auto-pilot/references/subagent-prompts.md`:
```text
Read and follow the skill at ../issue-resolver/SKILL.md to resolve issue #{N}.
Naming: see references/docs/naming-conventions.md.
Subagent prompt: references/agents/codebase-researcher.md.
```

`dist/plugin/skills/auto-pilot/references/subagent-prompts.md` (C-1, no `${CLAUDE_PLUGIN_ROOT}` available):
```text
Read and follow the skill at ../../issue-resolver/SKILL.md to resolve issue #{N}.
Naming: see ../../../docs/naming-conventions.md.
Subagent prompt: ../../../shared/agents/codebase-researcher.md.
```

The build emits exactly one form per **reference type** per output. Mixing forms *within the same reference type* (e.g., one `${CLAUDE_PLUGIN_ROOT}` shared-agent reference and one `../../../shared/agents/...` reference in `dist/plugin/`) is not allowed and Phase E aborts on detection. Mixing forms *across* reference types within a single file is expected for some ADR rows (see §6 decision matrix and §4 Phase E for the precise rule).

**Rule:** Authored prompts must never hardcode `skills/<name>/SKILL.md`. Cross-skill orchestration uses `{{skill:name}}` tokens.

The build rewrites logical references in all text-like files within a skill:

- `SKILL.md`
- `README.md`
- `references/**/*.md`
- `templates/**/*` (content rewritten, paths preserved)
- Other text-like extensions: `.txt`, `.yml`, `.yaml`, `.json`, `.toml`

Binary files (`.png`, `.jpg`, etc.) are copied as-is, never scanned.

### Special Case: `init-gitissue/templates/gitissue-template.yml`

This template is copied into the user's repo as `.gitissue.yml`. Any relative doc paths in its comments would resolve against the user's repo, not the skill install location.

**Rule:** Comments inside `init-gitissue/templates/gitissue-template.yml` reference runtime docs as absolute GitHub URLs pointing at `main`:

```text
# See https://github.com/luongnv89/idd/blob/main/src/docs/config-schema.md
```

**URL versioning trade-off (resolved):** v9 always uses `main`, same as v8. The alternative — pinning to release tags — would require the build to template URLs based on `src/plugin.json.in:version`, which adds machinery (placeholder syntax, build-time substitution, tag existence validation). Since these URLs are read by humans (in their installed `.gitissue.yml` comments) rather than consumed by runtime code, slight drift between user's installed version and `main` documentation is acceptable. The `main` URL is always a valid pointer to current documentation.

The build does not rewrite absolute URLs in this template. Enforcement is **two-layered**:

1. **Build-time check (Phase E):** Build aborts if any `https://github.com/luongnv89/idd/.../docs/<file>.md` URL appears where `<file>` exists in `src/docs/` — should be `src/docs/<file>.md` instead.
2. **Tests:** `tests/test-init-template-doc-urls-source.sh` verifies the source template before build; `tests/test-init-template-doc-urls-dist.sh` verifies the committed dist copy after build. The plugin copy is verified in CI by the same script run against the freshly built `dist/plugin/`.

## 4. Build Script Behavior

`./scripts/build.sh` is a stable entrypoint. It calls `python3 scripts/build.py` for safer parsing and manifest generation.

### 4.1 Determinism Invariants

The build is byte-deterministic so that CI's `git diff --exit-code dist/skills/` is meaningful. Identical inputs (`src/` + `scripts/build.py` + Python version) produce identical outputs on any machine, any wall-clock time.

Required guarantees:

1. **File traversal order:** `build.py` sorts directory listings lexicographically (UTF-8 byte order). No reliance on filesystem readdir order.
2. **JSON output:** `plugin.json` and any other generated JSON use sorted keys (`json.dumps(..., sort_keys=True, indent=2)`) and a trailing newline. No tabs.
3. **No timestamps:** Generated banners and any other generated content contain no wall-clock timestamps, build-host names, or user identifiers. The §4 Phase C banner is literal text only.
4. **Line endings:** All written text files use LF (`\n`). No CRLF. No mixed.
5. **No absolute paths:** Generated content never embeds the build machine's filesystem layout (e.g., `/Users/foo/...`). Reference paths are always repo-relative or output-relative.
6. **Stable Python version:** CI pins `python-version: "3.11"`. Local builds may use any 3.11.x; the build aborts on Python < 3.11.
7. **No randomness:** No UUIDs, no `os.urandom`, no `dict` insertion-order reliance for output (sort before serializing).

The CI drift check (§8) is the enforcement mechanism: any non-determinism produces a stale `dist/skills/` and fails CI on the next run on a different machine.

### Phase A — Inventory

1. Read `src/plugin.json.in` for plugin metadata. Substitution syntax: `${VAR}` placeholders only, resolved by `build.py` against this fixed substitution table:

   | Placeholder | Source |
   |---|---|
   | `${PLUGIN_SLUG}` | constant `idd` (or value chosen per §12 #1) |
   | `${PLUGIN_VERSION}` | release tag if building under a tag, else value from `src/plugin.json.in:default_version` |
   | `${PLUGIN_NAME}` | constant string in `plugin.json.in` |
   | `${PLUGIN_DESCRIPTION}` | constant string in `plugin.json.in` |
   | `${PLUGIN_AUTHOR}` | constant string in `plugin.json.in` |

   Unknown placeholders abort the build. No shell `envsubst`, no Mustache, no Jinja. Adding a new placeholder requires updating both `plugin.json.in` and the table in `build.py`.
2. Discover public skills from `src/skills/*/SKILL.md`.
3. Note internal skills (`src/internal-skills/*`) and deprecated skills (`src/deprecated-skills/*`) but do not build them by default. Deprecated skills may opt into public `dist/skills/` via a `distribute:` frontmatter flag — see §7.
4. Parse each skill's frontmatter for: name, description, version, effort, compatibility.
5. Scan every text-like file in each public skill for logical references and `{{skill:...}}` tokens.

### Phase B — Transitive Dependency Closure

For each public skill, compute the transitive closure of dependencies via DFS with cycle detection.

State:

- `visited`: files already fully processed (their outgoing edges have been traversed).
- `active_stack`: files currently on the active DFS path.

Algorithm:

1. Seed a worklist with logical references found by scanning the skill's text-like files.
2. For each reference `R`:
   a. If `R` is in `active_stack`, emit `⚠ cycle detected: A -> ... -> R` and continue (do not re-traverse).
   b. If `R` is in `visited`, skip silently — `R` is a shared dependency reached via multiple paths, not a cycle.
   c. Otherwise: push `R` to `active_stack`, resolve to its source path, scan its outgoing references, recurse, then pop from `active_stack` and add to `visited`.
3. Sort `visited` lexicographically before emission so output ordering is deterministic regardless of traversal order.
4. After traversal, `visited` is the complete dependency set for the skill.

This correctly distinguishes diamond dependencies (A → B, A → C, B → D, C → D — no cycle) from true cycles (A → B → A).

**Closure side effect (worth knowing):** A flattened skill's `references/docs/` may contain a doc its `SKILL.md` never names directly — pulled in transitively because a shared agent the skill *does* use references that doc. Example: `auto-pilot` references `shared/agents/implementer.md`, which references `docs/naming-conventions.md`; the flattened `auto-pilot` therefore ships `references/docs/naming-conventions.md` even if `auto-pilot/SKILL.md` never mentions it. The Phase C banner identifies these as generated. This is correct behavior — the skill is self-contained — but documenting it here prevents reader confusion.

Failure modes that abort:

- Unknown logical reference (file not found in `src/`).
- Reference outside allowed source roots (`src/shared/agents/` or `src/docs/`).
- Non-markdown file under `src/shared/agents/` or `src/docs/`.

### Phase C — `dist/skills/` (flattened)

For each public skill and any deprecated skill marked for distribution:

1. Copy authored directory to `dist/skills/<name>/`.
2. Copy all transitive-closure shared agents to `dist/skills/<name>/references/agents/`.
3. Copy all transitive-closure skill docs to `dist/skills/<name>/references/docs/`.
4. Prepend an HTML comment banner to each generated dependency copy (literal text only, no timestamps):

   ```html
   <!-- Generated from src/shared/agents/<file>.md. Do not edit. Edit source and run ./scripts/build.sh. -->
   ```

5. Rewrite logical references in all copied text-like files, including generated dependency copies, per the §6.0 ADR-decided form:
   - `shared/agents/X.md` → `references/agents/X.md`
   - `docs/Y.md` → `references/docs/Y.md`
   - `{{skill:name}}` → `/name` (A-1) or `../<name>/SKILL.md` (A-fail)
6. Copy `templates/` directories. Rewrite text content the same way except when the path is part of an absolute URL.

Each flattened skill has zero file dependencies outside its own directory.

### Phase D — `dist/plugin/`

1. Create:

   ```text
   dist/plugin/
   ├── .claude-plugin/plugin.json
   ├── skills/
   ├── shared/
   └── docs/
   ```

2. Copy public skills into `dist/plugin/skills/`. Internal and deprecated skills are excluded unless flagged.
3. Copy `src/shared/` and `src/docs/` into `dist/plugin/`.
4. Generate `dist/plugin/.claude-plugin/plugin.json` from `src/plugin.json.in` plus discovered skill metadata. JSON keys sorted, trailing newline, `${VAR}` placeholders resolved.
5. Rewrite `{{skill:name}}` tokens per the §6.0 ADR:
   - A-1: `/<plugin-slug>:name`
   - A-fail + B-1: `${CLAUDE_PLUGIN_ROOT}/skills/<name>/SKILL.md`
   - A-fail + B-fail + C-1: `../../<name>/SKILL.md`
6. Rewrite plugin-local shared/doc references per the §6.0 ADR:
   - B-1: `${CLAUDE_PLUGIN_ROOT}/shared/agents/X.md` and `${CLAUDE_PLUGIN_ROOT}/docs/Y.md`
   - B-fail + C-1: `../../../shared/agents/X.md` and `../../../docs/Y.md` (from `dist/plugin/skills/<name>/references/X.md`, three levels up reaches plugin root)
7. If the §6.0 ADR has no working strategy for plugin output (all three experiments failed), the plugin build aborts with a clear error pointing at the ADR.

### Phase E — URL-Aware Scanning and Sanity Checks

URL-awareness rules apply to all scanning and rewriting:

- A match inside `http://` or `https://` URL text is treated as a remote URL. The build does not rewrite these or require them to exist locally.
- Bare paths like `docs/config-schema.md` are local references and must be rewritten or copied.
- Markdown link syntax (`[text](url)`) is parsed: URL targets are checked against the URL-prefix rule.

**Stale-doc URL detection (generalized).** For every GitHub URL of the form `https://github.com/luongnv89/idd/.../docs/<file>.md` found in any text-like file, the build checks whether `<file>` exists in `src/docs/`. If it does, the URL is stale (post-move it should reference `src/docs/<file>.md`) and the build aborts with a clear error pointing at the file and line. This survives future doc additions without per-file enumeration.

**`init-gitissue` template URL rule (build-time check).** As part of Phase E, before writing dist outputs, the build scans `src/skills/init-gitissue/templates/gitissue-template.yml` for any `https://github.com/luongnv89/idd/.../docs/<file>.md` URL and aborts if `<file>` exists in `src/docs/` (must be `src/docs/<file>.md`). This complements the test in §9 — the build catches drift at source-tree edit time, the test catches it post-hoc.

**Plugin manifest schema validation.** `scripts/plugin-schema.json` is a **best-effort** schema:

- Authored from public Claude Code plugin documentation at the time of creation. The file's top-level comment includes a `derivedFrom:` line citing the docs URL and the date.
- Re-validated whenever Claude Code releases plugin-related changes; tracked as a §13 non-goal-cadence item with a quarterly check.
- Authoritative gate is `claude plugin validate` when the CLI exposes it. The build first runs `claude plugin --help` and uses the validate subcommand if present. If absent, the build falls back to `scripts/plugin-schema.json`. When both are available, the CLI overrides the local schema; a CLI failure aborts even if the schema check passes.

Build aborts with a clear error if any of:

- Any flattened skill contains an unresolved local logical reference: `shared/agents/`, runtime `docs/*.md`, `skills/<name>/SKILL.md`, or `{{skill:...}}`.
- Any flattened skill local reference points outside its own directory.
- Any referenced source doc is missing from `src/docs/`.
- Any copied generated dependency still contains an unresolved local logical reference.
- Any plugin skill still contains an unresolved `{{skill:...}}` token.
- Any plugin output reference uses a form not listed in the chosen §6 decision matrix row, **or** any single reference type (cross-skill, shared-agent, runtime-doc) is rendered two different ways within `dist/plugin/`. Note that legitimate ADR rows mix *different* forms across reference types — e.g., row (A-1, B-fail, C-1) produces `/<plugin-slug>:<name>` for cross-skill calls and `../../../shared/agents/X.md` for shared agents in the same file; that is correct, not a mix. The build aborts only when the *same* reference type appears in two forms.
- Any plugin skill still contains a bare local `shared/agents/` or runtime `docs/*.md` reference instead of the ADR-decided form.
- The §6 ADR has no committed decision matrix entry for the resolved (A, B, C) outcome triple.
- Any GitHub URL referencing `docs/<file>.md` where `<file>` exists in `src/docs/` (stale-doc detection).
- `.claude-plugin/plugin.json` is missing, or fails `claude plugin validate` when available, or fails `scripts/plugin-schema.json` when not.
- A non-markdown file is found under `src/shared/agents/` or `src/docs/`.

## 6. Auto-Pilot Rewrite

**BLOCKER — runtime experiments required before PR 3.** Three assumptions need validation:

- **A:** Does a subagent receiving "Use the `/issue-resolver` skill" actually invoke it?
- **B:** Does a subagent prompt containing `${CLAUDE_PLUGIN_ROOT}` resolve the variable to the plugin root?
- **C:** Does a subagent receiving a sibling-relative path like `../../issue-resolver/SKILL.md` (from a plugin skill's `references/` file) successfully read the target?

### §6.0 Validation Experiments

Procedure lives in `docs/experiments/cross-skill-invocation.md`. Experiments A, B, and C are all mandatory. Running all three is required to populate the §6 decision matrix unambiguously.

#### Experiment Bootstrap: Test Plugin Scaffold

Experiments B and C must run inside a real Claude Code plugin context. PR 2 includes `scripts/build-test-plugin.sh`, which:

1. Runs the standard `build.py` against `src/` to produce a temporary `dist/test-plugin/` tree (same shape as `dist/plugin/`, distinct path so it doesn't shadow CI output).
2. Emits a minimal hand-curated `.claude-plugin/plugin.json` with slug `idd-test`. Skills referenced by the experiments (`issue-creator`, `issue-resolver`) plus their transitive shared/doc closure are included; everything else is omitted to keep the scaffold small.
3. Prints install instructions — copy or symlink `dist/test-plugin/` into the local Claude Code plugins directory, restart, and run the experiment prompts.

The scaffold is throwaway: `dist/test-plugin/` is git-ignored, and `scripts/build-test-plugin.sh` is removed in PR 3 once the production build is the source of truth. The §6.0 ADR records the **commit SHA of PR 2 (the source-tree state used during experiments)**, not a path to a still-present file. A future maintainer re-running the experiments would `git checkout <SHA>`, recover `build-test-plugin.sh` from history, regenerate the scaffold, and re-run.

#### Experiment A — Slash-command resolution in subagents

Spawn a one-off Agent with this prompt:

```text
Use the /issue-creator skill to draft an issue titled "Test issue" with body "smoke test".
Report back the resulting issue body in JSON.
```

Outcomes:

- **A-1: Auto-resolves.** Subagent invokes `/issue-creator` and returns templated body.
- **A-fail: Treats as text or partial.** Subagent guesses based on the skill name, errors, or works inconsistently across harnesses. Use sibling-relative fallback for portability.

#### Experiment B — `${CLAUDE_PLUGIN_ROOT}` expansion in plugin subagent prompts

Run inside the test plugin scaffold using a subagent prompt, not a top-level shell command. The test must prove expansion works from the same kind of prompt file that `auto-pilot` will use after build (`dist/plugin/skills/auto-pilot/references/subagent-prompts.md`).

```text
Read these files and report the first heading from each:
1. ${CLAUDE_PLUGIN_ROOT}/skills/issue-creator/SKILL.md
2. ${CLAUDE_PLUGIN_ROOT}/docs/naming-conventions.md
3. ${CLAUDE_PLUGIN_ROOT}/shared/agents/codebase-researcher.md
```

Outcomes:

- **B-1: Resolves.** Subagent reads all three files and reports expected headings.
- **B-fail: Does not resolve** (treats variable as literal, errors, or returns empty).

#### Experiment C — Sibling-relative paths in plugin subagents

Run inside the test plugin scaffold. From a plugin skill's `references/` file, the path `../../<name>/SKILL.md` reaches a sibling skill's root; `../../../shared/agents/X.md` reaches the plugin-root shared dir. Test prompt placed in `dist/test-plugin/skills/auto-pilot/references/c-test.md`:

```text
Read these files and report the first heading from each:
1. ../../issue-creator/SKILL.md
2. ../../../docs/naming-conventions.md
3. ../../../shared/agents/codebase-researcher.md
```

Spawn a subagent with this exact parent prompt:

```text
Read dist/test-plugin/skills/auto-pilot/references/c-test.md and follow its
instructions exactly. Report results in JSON with keys: file_1_heading,
file_2_heading, file_3_heading, errors (array of strings).
```

The parent prompt is the unit under test, not a template — re-runs use this verbatim so outcomes are comparable.

Outcomes:

- **C-1: Resolves.** Subagent reads all three files relative to the prompt file's location.
- **C-fail: Does not resolve** (subagent CWD differs from prompt file location, paths fail).

### Durable artifact

Record all three experiment outcomes in `docs/decisions/cross-skill-invocation.md` (ADR format: context, decision, consequences, scaffold commit SHA). The ADR specifies which rendering strategy the build implements per output:

|---|---|---|---|---|
| 1 | 1 | any | `/<name>` | `/<plugin-slug>:<name>`; shared/docs use `${CLAUDE_PLUGIN_ROOT}/...` |

Note that Experiment C unblocks the (A-fail, B-fail) cell that v8 left as a dead end. The standalone form `../<name>/SKILL.md` was not in question — flattened skills live as siblings under one skills directory by SKILL.md convention. C tests the plugin-tree analog.

ADR is committed before PR 3 opens. PR 3 description references it. PR 3 build script implements the chosen strategy.

**Flake protocol:** Each experiment is run **three times** with the parent prompts above. Record raw subagent outputs in the experiment log alongside the ADR. If results are 3-of-3 consistent, the outcome is decisive. If 2-of-3 or worse, run three more; document raw outputs of all six. A 3-of-6 split or worse is treated as `fail` for that experiment and noted as "non-deterministic in this harness" — the build picks the failure-row strategy. This avoids an ambiguous "is it flaky or broken" debate at PR-3 implementation time.

**Re-validation:** If Claude Code or another target harness changes behavior, rerun the experiments per `docs/experiments/cross-skill-invocation.md`, append a dated entry to the ADR, and adjust build rendering. The test plugin scaffold can be regenerated by checking out the PR-2 commit SHA recorded in the ADR.

**Owner:** whoever picks up PR 2. **Block:** PR 3 cannot start until the ADR is committed.

## 8. CI Drift Check

`.github/workflows/dist-check.yml`:

```yaml
name: dist-check

on:
  pull_request:
  push:

jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      # Source-level checks (run before build for fast failure)
      - run: bash tests/test-init-template-doc-urls-source.sh

      # Build both trees. Plugin tree is built fresh in CI, never committed.
      - run: ./scripts/build.sh

      # Drift check — only dist/skills/ is committed and must match.
      - run: |
          if ! git diff --exit-code dist/skills/; then
            echo "::error::dist/skills/ is out of date. Run ./scripts/build.sh and commit the result."
            exit 1
          fi

      # Dist-level checks — run against freshly built trees regardless of commit status.
      - run: bash tests/test-build-script.sh
      - run: bash tests/test-init-template-doc-urls-dist.sh
      - run: bash tests/test-flattened-self-contained.sh
      - run: bash tests/test-plugin-layout.sh
      - run: bash tests/test-plugin-reference-rendering.sh
      - run: bash tests/test-autopilot-portability.sh
      - run: bash tests/test-flattened-coexistence.sh
      - run: bash tests/test-dependency-closure.sh
      - run: bash tests/test-build-determinism.sh

  release:
    needs: drift
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: ./scripts/build.sh
      - run: tar -czf idd-plugin-${{ github.ref_name }}.tar.gz -C dist plugin
      - uses: softprops/action-gh-release@v2
        with:
          files: idd-plugin-${{ github.ref_name }}.tar.gz
```

## 12. Decisions and Open Questions

1. **Plugin slug:** `idd` or `gitissue`? Affects every plugin command (`/idd:issue-resolver` vs `/gitissue:issue-resolver`). Recommend `idd`.
2. **Versioning policy:**
   - Plugin version = bundle release version, lives in `src/plugin.json.in` as `${PLUGIN_VERSION}`.
   - Skill versions = independent, in each skill's frontmatter.
   - `plugin.json` carries plugin version only.
   - README skill table carries skill versions only.
3. **Manifest source:** Plugin metadata authored in `src/plugin.json.in`; skill list generated from discovery. `${VAR}` placeholders only.
4. **Text scanning:** Allowlist-by-extension: `.md`, `.txt`, `.yml`, `.yaml`, `.json`, `.toml`. Binaries copied as-is.
5. **Runtime doc URL versioning (resolved):** Always use `main`. Pinning to release tags would require build-time URL templating; since these URLs are read by humans in installed `.gitissue.yml` comments, slight drift is acceptable. The `main` URL is always a valid pointer to current docs.
6. **`issue-pr-review-fix-loop` removal timing:** Recommend remove from public dist in PR 2. Source retained under `src/deprecated-skills/` for one more release.
7. **Cross-skill resolution behavior:** Run §6.0 experiments A/B/C in PR 2 against the throwaway test-plugin scaffold. Outcomes recorded in `docs/decisions/cross-skill-invocation.md`. Build implements rendering strategy per the §6 decision matrix.
8. **Banner format:** HTML comments only, literal text only (no timestamps, no host info — required by §4.1 determinism). Enforced by the markdown-only invariant for shared agents and runtime docs.
9. **Plugin distribution model:** `dist/plugin/` is built in CI and shipped as a release tarball, not committed. Users install via the release artifact or `claude plugin install`. Reduces repo diff surface and removes "two trees forever in sync" maintenance burden.
10. **Plugin schema provenance:** `scripts/plugin-schema.json` is best-effort, derived from public Claude Code plugin docs at authoring time. The file contains a `derivedFrom:` comment with source URL and date. `claude plugin validate` overrides the local schema when available. Quarterly review cadence to catch upstream changes.
