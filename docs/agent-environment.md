# Agent Environment Notes

What an agent needs to work this repository autonomously. Everything here is
verified against the repo as of issue #330.

## Toolchain

| Tool | Requirement | Notes |
|------|-------------|-------|
| bash | any POSIX-capable bash | build and all tests are shell scripts |
| python3 | >= 3.11 | enforced by `scripts/build.sh` preflight (exits 1 on older versions) |
| git | any modern git | branch/commit/PR workflow only |
| gh CLI | authenticated (`gh auth login`) | every call must use `--json` with explicit field selection |

No package manager or third-party dependencies are required — build and tests
rely on the Python standard library and shell built-ins.

## Environment

- No required environment variables.
- `GITHUB_TOKEN` is only needed where a skill or script calls `gh` and gh is
  not already authenticated via `gh auth login`; standard gh auth is
  sufficient otherwise.
- No virtualenv needed: there is no runtime code, only skill sources,
  build scripts, and shell tests.

## Recorded commands

Build (compiles skills into an output directory, verifies them; with a custom
`--out` it does **not** promote to the repo-root `skills/`):

```bash
bash scripts/build.sh --out <tmp-dir> --quiet
```

Test (runs every tracked test script; integration tests are shell scripts in
`tests/`):

```bash
git ls-files 'tests/*.sh' | xargs -n1 bash
```

## Verification

Both commands were run green at audit time (issue #330):

- Build: exit 0, no output (`--quiet` suppresses stdout on success).
- Tests: all 61 tracked scripts under `tests/*.sh` exited 0
  (`git ls-files 'tests/*.sh' | wc -l` → 61).

Note: some tests intentionally print `✗ ...` lines as expected output of
negative cases (e.g. the idd-lint / template-parity validators rejecting bad
input). A `✗` line in test output is not a failure by itself — the per-script
exit code and its final `Result:` / `Failed:` counter are authoritative.

## Repo etiquette

- **Skills-only repo.** There is no application runtime. Authored sources live
  under `src/`; committed installable copies live under `skills/` and are
  regenerated by `scripts/build.sh`. Never hand-edit `skills/` — edit
  `src/skills/<name>/SKILL.source.md`, then run the recorded build command.
- **Docs placement rule** (issue #81). All documentation lives in top-level
  `docs/`. Runtime docs (referenced by skills via bare `docs/X.md` tokens) sit
  at the top level of `docs/` and get bundled into each skill's
  `references/docs/` at build time. Project docs (humans only) go top-level or
  under a topical subdirectory (`docs/decisions/`, `docs/experiments/`,
  `docs/release-notes/`). If a skill reads it at runtime, it is a runtime doc.
- **gh --json rule.** Every `gh` invocation must use `--json` with an explicit
  field selection (e.g. `gh issue view 42 --json number,title,body,labels`).
  Never parse text output from `gh`.
- **Output symbols** (see `DESIGN.md`). Terminal output uses a fixed symbol
  vocabulary: `✓` success, `✗` failure/error, `●` in progress, `◆` section
  header, `⚡` action/recommendation, `⚠` warning, `○` info/neutral. Section
  separators use `┄`, tables use `│ ─ ┼`, content under headers is indented
  two spaces, URLs always sit on their own line.
